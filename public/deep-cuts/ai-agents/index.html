A library errand with a few things that could go wrong.

The errand

One book before six.

It’s 4:20 p.m. and you need a copy of The Moon Atlas for a library display. You can collect it by six. You need a step-free entrance and you have a budget of exactly zero dollars.

You could search the catalog, cross-check opening hours and the entrance, then request a hold. Or you could hand over the errand. “Find me a copy I can pick up by six,” you say. “Check access and ask me before placing a hold.”

A chatbot could tell you how to search. A tool-using assistant could look up the title. But halfway through this errand, the first copy can disappear. Now the system needs to decide what to do with that information. That’s when the system has to choose a different path.

We’ll follow a fictional library network. Its tools, hours, books, and receipts are simulated. The decisions are the part to watch.

Inside the loop

One decision at a time.

An AI agent, in the sense used here, is a system that pursues a goal by choosing actions, observing what happens, and choosing again. In a language-model agent, the model helps choose the next action. The surrounding software keeps track of the task, grants access to tools, and enforces the limits. People sometimes use agent more broadly. The useful question is how much control the model has over what happens next.

Goal

Carry the title and deadline forward with the budget and access requirements. The agent may search right away. A reservation needs the reader’s approval.

Action

The model requests a catalog search. The application checks the arguments, makes the call, and returns structured results. Central Library appears to have a copy.

Observation

Central’s branch system reports that its last copy just went out. The catalog was showing an older snapshot. The search result was useful, and the newer evidence changes what the agent should do.

Next decision

Check the next candidate. Ask if a requirement is ambiguous. Stop if nothing qualifies. The result of one step shapes the choice of the next.

Some systems write a plan at the start. Some pick one action at a time. A plan can help organize a big job, but the loop is what lets it react when a date changes or a tool returns something unexpected. The ReAct paper explored an early version of this pattern, alternating model reasoning and actions so that new observations could change the next move. [1]

Run the agent

Watch an errand go sideways.

Start with the stale catalog. You’ll see what each tool returned, why the next call was chosen, and what it takes to claim the errand is done. At the approval gate, you make the decision.

Try Lost receipt next. Suppose the branch places the hold but the reply never arrives. The timeout tells us the response failed to reach us. The hold could still exist. Checking its status avoids a second request. A real service can help by accepting an idempotency key, a request identifier it uses to recognize a retry of the same operation.

Now try Neither branch works. A good final message explains what was checked and where the task fell short. Maybe the only copy requires stairs. Maybe the deadline passed. The system can offer alternatives, but changing “step-free” or “today” is the reader’s decision. Stopping can be the correct outcome even when the original request remains unmet.

What a tool call buys you

The model can produce plausible words about the library. A catalog tool gives the system a way to ask the library itself. The tool definition tells the model which inputs are accepted and what the response means. A timestamp can tell it how old the answer is. An error code can tell it what failed. A stable branch ID keeps “Central” from being confused with another location carrying the same name.

The model sees the answer because the application puts the result back into the next turn. The application can also reject an invalid request before sending it. The model can interpret a messy user request, and the tool can insist on a branch ID, an exact book record, and a valid approval before attempting a hold.

Where the state lives

As the agent runs, it needs to know the goal, which branches were checked, the current candidate, whether the person approved that exact hold, and whether a receipt came back. The recent conversation can carry some of that context. An application should record consequential facts and approvals explicitly, especially if a run can pause and resume.

Memory can also mean a preference or record that survives across sessions. “I usually pick up at Cedar” might help rank two valid branches next time. It should never silently take precedence over “I need step-free access today.” Working state answers what happened in this run. Long-term memory can inform a future one.

Who decides?

Same request, three ways to handle it.

Look at where the next step comes from. A person can choose it. A programmer can define it ahead of time. Or the model can choose among actions based on intermediate results. Two systems can look identical from the chat box and work very differently under the hood. [2]

A fixed workflow can branch and retry. You might write a rule that checks every branch with stock, discards any branch with stairs, and sorts the survivors by pickup time. That could be the best answer for this errand. Where the requirements become harder to encode, like interpreting two contradictory accessibility notices or identifying when a vague request needs clarification, giving the model a choice of next steps can help.

Most practical designs are hybrids. A model might interpret a request and choose a lookup. Ordinary software can enforce the deadline, check the tool’s inputs, and make the approval gate impossible to skip. You can make that system more predictable without taking away the flexibility it needs.

Where is the extra judgment worth it?

Suppose the job is sending the same due-date notice every week. A scheduled rule is easy to test and gives the same result for the same inputs. Now suppose the job is triaging a pile of patron requests written in different ways. A model can interpret what people asked for and choose the right lookup or form. The cost of that flexibility is more calls, more time, and more ways a run can surprise you.

Look for a task with a clear end state, tools that can report what happened, and permission boundaries you can enforce. “Help with the library” leaves the agent guessing about both scope and success. “Find one eligible copy and show me where I can collect it” gives it a target you can check.

Does it need a team?

Sometimes a coordinator delegates work to several specialized agents. One might gather catalog records while another checks accessibility. That helps when the tasks are genuinely independent or need different tools. It also introduces handoffs, repeated calls, and decisions about what to do when results disagree. In the library example, two ordinary reads can run in parallel inside one agent. A team adds value only if it solves a problem the simpler design actually has.

What breaks

Good at a step. How about ten?

Imagine a brittle errand with ten required steps and no recovery. Even if a step goes right 95% of the time given that everything before it went right, the chance of a clean ten-step run is about 60%. That’s 0.95 multiplied by itself ten times. Try adding steps and watch the difference between a strong local result and a full task.

Real calls fail for different reasons. A catalog outage can knock out several steps at once. A reliable verification step can catch a bad result before a write. A second attempt can help if a network problem was brief, but it’s costly if the input is wrong or the service is still down. The point of the toy model is to show how many small assumptions can sit between a fluent answer and a completed job.

So how would we evaluate the library agent? Give it realistic errands with cases it hasn’t seen. Score whether it secured a qualifying copy, avoided duplicate holds, preserved access and cost constraints, and asked before taking action. Track time and tool usage. Include trials where there is no valid option. Compare the agent with a simple scripted baseline on the same cases. A system that finds an extra copy once in a while can still be a poor fit if it regularly needs intervention or places duplicate holds. Read the traces for failures. “I reserved the book” sounds equally confident with or without a receipt.

The trace is the record of what the system did. Tool names, arguments, observed results, approval decisions, and final status can make a run inspectable. These records can contain private information, so real systems need rules about what to save and who can see it. You can debug a duplicate reservation from logged tool calls and receipts without collecting every internal detail of the model.

What it can do

Access and permission are different.

The catalog can tell you a copy exists. A hold tool can change who gets the next copy. Those actions have different consequences. Good tools make that visible: a read returns evidence, a write requires the right authority, and a successful write returns something the system can verify.

Evidence

“One copy available.”

A branch record informs the decision.

Authority

“Yes, hold it at Cedar.”

The requester authorizes this specific action.

Confirmation

“Hold confirmed. H-284.”

A receipt supports the claim that it happened.

An agent may read web pages, documents, or tool output written by people outside the conversation. That material can contain instructions directed at the model. Treating those instructions as authorization is a failure called indirect prompt injection. A library listing can provide evidence about a book. It can’t expand an agent’s access or change who approved a hold. Research like AgentDojo measures how tool-using systems handle such untrusted data. [3]

Keep permission checks in the application and tool layer. Give each tool the access it needs. Ask before actions with material consequences, and tie the approval to the exact item, branch, and price. Put a limit on retries and calls, and give the agent a clear way to stop or ask. The model can recommend a move. The system decides whether that move is allowed. [4]

Now go back to 4:20. The telling moment was the decision after Central’s last copy went out. The system had evidence, a goal it could still pursue, and a choice about what to do next.

The moment worth watching is the one after the plan stops working.
